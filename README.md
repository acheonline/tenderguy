# tenderguy

Система подготовки и проверки пакета документов тендерных заявок (44-ФЗ/223-ФЗ).
Проект находится в фазе PoC: реализуется конвейер анализа пакетов заявок —
сканирование каталога документов, классификация файлов (.docx/.xlsx/.pdf),
далее по плану — парсинг содержимого и проверки консистентности.

## Требования

- **Go 1.24.4+** (версия зафиксирована в `go.mod`);
- **golangci-lint** (для локального линта, правила в `.golangci.yml`):
  ```bash
  go install github.com/golangci/golangci-lint/cmd/golangci-lint@v1.64.5
  ```
- **системные инструменты для разбора PDF** (команда `parse-pdf` и её тесты):
  текстовый слой читает poppler, скан-страницы распознаёт Tesseract с русским
  языковым пакетом; сборка требует dev-пакеты (cgo-биндинг к libtesseract):
  ```bash
  sudo apt-get install -y poppler-utils tesseract-ocr tesseract-ocr-rus \
      libtesseract-dev libleptonica-dev
  ```

## Локальный запуск

CLI `tenderguy` обходит каталог с документами и классифицирует файлы по типу
(по расширению и сигнатуре содержимого), командой `parse-docx` извлекает из
`.docx` текст и таблицы, командой `parse-xlsx` — ячейки и формулы книг Excel,
командой `parse-pdf` — текст из PDF: текстовый слой
или OCR Tesseract для отсканированных страниц, командой `extract-reqs`
поверх этих парсеров собирает карточку реквизитов документа, командой `trace`
проверяет, что у каждого фрагмента и каждого реквизита есть адрес в источнике —
«файл + страница/пункт» (P1.6), командой `metric` замеряет H1 — долю успешно
разобранных документов пакета против порога 80 % (P1.7), а командой `dump-docs`
сохраняет все извлечённые данные пакета в `docs.json` (P1.8).

```bash
go run ./cmd/tenderguy --input-dir <каталог> [--format text|json]
go run ./cmd/tenderguy --command parse-docx --file <документ.docx> [--with-text] [--format text|json]
go run ./cmd/tenderguy --command parse-xlsx --file <книга.xlsx>   [--with-text] [--format text|json]
go run ./cmd/tenderguy --command parse-pdf  --file <документ.pdf>  [--with-text] [--format text|json]
go run ./cmd/tenderguy --command extract-reqs (--file <документ> | --input-dir <каталог>) [--format text|json]
go run ./cmd/tenderguy --command trace (--file <документ> | --input-dir <каталог>) [--with-text] [--format text|json]
go run ./cmd/tenderguy --command metric --input-dir <каталог> [--format text|json]
go run ./cmd/tenderguy --command dump-docs --input-dir <каталог> --output-dir <каталог-для-docs.json>
```

Флаги:

| Флаг | Обязательный | Описание |
|---|---|---|
| `--command` | нет | `scan` (по умолчанию — обход и классификация), `parse-docx` (текст и таблицы), `parse-xlsx` (ячейки и формулы), `parse-pdf` (текстовый слой и OCR), `extract-reqs` (карточка реквизитов), `trace` (адреса фрагментов и трассируемость), `metric` (доля разобранных документов, H1) или `dump-docs` (выгрузка всех данных в `docs.json`) |
| `--input-dir` | да для `scan`, `metric` и `dump-docs` | каталог с документами: обход для `scan`, все `.docx`/`.xlsx`/`.pdf` каталога для команд разбора, `extract-reqs` и `trace`, все поддерживаемые документы пакета для `metric`, полный список файлов обхода для `dump-docs` (пути в коде не хардкодятся) |
| `--output-dir` | да для `dump-docs` | каталог, куда пишется `docs.json` (создаётся, если его нет); с другими командами не передаётся |
| `--file` | нет | один документ (`.docx`, `.xlsx` или `.pdf`) для разбора — альтернатива `--input-dir`, вместе с ней не передаётся; для `dump-docs` и `metric` не используется — обе команды обходят весь каталог |
| `--with-text` | нет | вывести извлечённый текст целиком (по умолчанию — только сводка); у `trace` печатает список фрагментов с адресами; для `extract-reqs`, `dump-docs` и `metric` не передаётся — отчёт `metric` содержит счётчики, а не тексты документов |
| `--format` | нет | формат отчёта: `text` (по умолчанию) или `json` |

Примеры:

```bash
# текстовый отчёт по каталогу с документами заявки
go run ./cmd/tenderguy --input-dir "./docs/НЭО поставка RedCheck"

# машиночитаемый JSON-отчёт
go run ./cmd/tenderguy --input-dir ./docs --format json

# разбор одного документа: сводка и вердикт полноты извлечения
go run ./cmd/tenderguy --command parse-docx --file "./docs/НЭО поставка RedCheck/Тендерная документация/226717 ЗД ЭФ (К, КП, ЗП).docx"

# все .docx каталога вместе с извлечённым текстом
go run ./cmd/tenderguy --command parse-docx --input-dir ./docs --with-text

# разбор спецификации .xlsx: сводка по листам, формулы и вердикт полноты
go run ./cmd/tenderguy --command parse-xlsx --file "./docs/НЭО поставка RedCheck/Тендерная документация/Приложение 1_ТЗ/226717_671.26.00374_ТЕХ.xlsx"

# все книги каталога вместе с содержимым (TSV-сеткой каждого листа)
go run ./cmd/tenderguy --command parse-xlsx --input-dir ./docs --with-text

# разбор PDF: текстовый слой читается сразу, скан-страницы уходят в OCR
go run ./cmd/tenderguy --command parse-pdf --file "<каталог>/Заявка.pdf"

# все PDF каталога в машиночитаемом отчёте (JSON)
go run ./cmd/tenderguy --command parse-pdf --input-dir "<каталог>" --format json

# карточка реквизитов одного документа: ИНН/КПП/ОГРН, даты и суммы
go run ./cmd/tenderguy --command extract-reqs --file "./docs/НЭО поставка RedCheck/Тендерная документация/226717 ЗД ЭФ (К, КП, ЗП).docx"

# карточки всех документов пакета — то, с чего начинает сверку P2
go run ./cmd/tenderguy --command extract-reqs --input-dir "./docs/ТЭК СПб сервис WAF" --format json

# трассируемость пакета: доля фрагментов и значений с адресом в источнике
go run ./cmd/tenderguy --command trace --input-dir "./docs/НЭО поставка RedCheck"

# список фрагментов с адресами по одному документу — что увидит P2 в замечании
go run ./cmd/tenderguy --command trace --file "./docs/НЭО поставка RedCheck/Тендерная документация/226717 ЗД ЭФ (К, КП, ЗП).docx" --with-text

# замер H1 по пакету: доля успешно разобранных документов против порога 80 %
go run ./cmd/tenderguy --command metric --input-dir "./docs/ТЭК СПб сервис WAF"

# тот же замер в машиночитаемом виде — процент, вердикт, разбивка по форматам
go run ./cmd/tenderguy --command metric --input-dir "./docs/НЭО поставка RedCheck" --format json

# выгрузка всех извлечённых данных пакета в ./out/neo/docs.json
go run ./cmd/tenderguy --command dump-docs --input-dir "./docs/НЭО поставка RedCheck/Тендерная документация" --output-dir ./out/neo

# проверка приёмки выгрузки: записей столько же, сколько файлов нашёл обход
jq 'length' ./out/neo/docs.json
```

`dump-docs` пишет одну запись на каждый файл обхода — не только на разбираемые:
у архива или служебного файла `text_content` и `fragments` пустые, а причина в
`note`, поэтому сверить выгрузку с описью пакета можно механически. Запись
содержит `file_path` (относительный путь от `--input-dir`), `doc_type`,
`text_content` (текст и таблицы документа), `metadata` (`inn`, `kpp`, `dates` —
то, что ищет `extract-reqs`) и `fragments` с адресами P1.6; списки `metadata`
всегда присутствуют и пусты как `[]`, а не как `null`, чтобы «нет значений»
отличалось от «забыли поле». Ожидаемый результат — строка сводки вида
`Записей в ./out/neo/docs.json: 11 (поддерживаемых 9, не разобрано 0)`.

Два свойства выгрузки важны для её потребителя:

- `file_path` относительный (от `--input-dir`), а адреса фрагментов и путь в
  `failed` сохраняются в том же виде, в каком оператор передал вход: при
  относительном `--input-dir` оба относительные, при абсолютном — абсолютные.
  Это не разнобой, а контракт `trace` из P1.6: адрес значения обязан совпасть с
  адресом фрагмента, поэтому переписывать его выгрузка не вправе.
- `metadata` — значения из парсера без признака валидности: сверка контрольных
  чисел и пометка подозрительных значений остаются за `extract-reqs`, а адрес
  любого значения при этом всегда виден в `fragments`.

Пакет с отсканированными PDF разбирается через OCR, поэтому прогон `dump-docs`
по нему занимает минуты — на закупочной документации НЭО замер составил 3m34s.

Разбор показывает счётчики (абзацы, таблицы, строки, ячейки, символы) и сверяет
их с `document.xml`: если текстовый фрагмент исходника не дошёл до модели, отчёт
назовёт его и вернёт код 1 — «извлечено без потерь» проверяется по факту, а не на глаз.
Сверка полноты сравнивает фрагменты дословно, без обрезки пробелов: показ может
обрезать пробелы (в том числе неразрывные) по краям ячеек таблицы, потерей это не
считается.

`parse-xlsx` читает книги Excel (`github.com/xuri/excelize/v2`): значения ячеек
уже отформатированы стилями числа, формулы отдаются текстом (общие shared-формулы
excelize переводит в каждой клетке), слияния и скрытые листы видны в отчёте —
скрытый лист читается так же полностью, как видимый. Эталон полноты считается
независимо от библиотеки по XML самого файла: каждая ячейка листа с содержимым
(`<v>` или `<f>`) обязана дойти до модели значением либо формулой; критерий
«все строки спецификаций прочитаны» — это пустой список потерь. Потерянные
адреса отчёт называет поимённо («лист «Шаблон» G16»), код выхода при этом 1.

`parse-pdf` работает постранично: текстовый слой читает `pdftotext`, а страницу с
меньше чем 12 непробельными символами считает сканом — растеризует её `pdftoppm`
в PNG под 150 dpi и распознаёт Tesseract (rus+eng). Отчёт показывает страницы с
разбивкой «текстовый слой / OCR», объём извлечённых символов и вердикт: «без
потерь» — если пустых страниц не осталось; распознанные и нераспознанные страницы
видны в замечаниях. Если на скан-странице OCR-инструменты не установлены, файл
попадает в «Ошибки разбора» с указанием, какой пакет нужен.

`extract-reqs` собирает карточку реквизитов по содержимому, которое уже умеют
извлекать `parse-docx`, `parse-xlsx` и `parse-pdf`, — своего парсера формата у
неё нет. Из содержимого берутся ИНН (10 и 12 цифр), КПП, ОГРН и ОГРНИП, даты
(`ДД.ММ.ГГГГ`, `ДД/ММ/ГГГГ` и «12 мая 2026») и суммы с валютным маркером.
Значение нормализуется (`2 617 844,26` и `2,617,844.26` — одно и то же число,
дата приводится к `ГГГГ-ММ-ДД`), повторы одного значения сливаются в одну
строку со счётчиком `×N`, рядом печатается ближайшая метка (`[метка: ИНН]`) и
его адрес в источнике (`@ стр. 2 · абз. 17`, `@ ТЗ!B7`, `@ стр. 5`) — с P1.6
карточка отвечает не только «что», но и «где»; если адресов несколько, второй и
следующие сворачиваются в `(+N)`, а в `--format json` у значения лежит полный
список `refs` (до 10 адресов и `ref_total` — всего).

Что и как проверяется:

| Вид | Проверка |
|---|---|
| ИНН(10), ИНН(12) | контрольные цифры по методикам ФНС |
| ОГРН, ОГРНИП | контрольная цифра `(2 × первые N−1 цифр) mod 11 mod 10` и допустимая первая цифра |
| КПП | только разрядность и код региона: контрольной цифры у КПП нет, последние три знака — порядковый номер постановки на учёт |
| Дата | календарь (високосный год, длина месяца) и границы 1900 … текущий+15 лет |
| Сумма | читаемость числа; валютный маркер обязателен |

Не прошедшее проверку значение из карточки не выбрасывается, а помечается `✗`
с причиной — расходящиеся реквизиты и есть предмет сверки P2. Поэтому
подозрительные значения не меняют код выхода: прогон остаётся 0, их видно в
отчёте и в сводке в stderr. Код 1 команда возвращает, если хотя бы один
документ не разобрался (такие файлы уходят в раздел «Ошибки разбора») или если
у найденного значения нет адреса в источнике: после P1.6 это отдельная
проверяемая карточкой вещь, а не мелочь вывода.

Числа без валютного маркера суммами не считаются: в таблицах спецификаций это
цена единицы или количество, контекст для них берётся из шапки столбца, и это
работа P2. Пустая карточка объясняет себя в замечаниях: «текст документа пуст»
значит правку ищут в парсере формата, «ИНН/ОГРН не найдены» — что в документе
этих реквизитов действительно нет (так бывает с отсканированными формами без
OCR и с пустыми шаблонами форм).

`trace` (P1.6) проверяет критерий PoC «100 % трассируемости»: раскладывает
каждый документ на фрагменты с адресами и считает, сколько из них адреса не
получили — и отдельно, сколько значений реквизитов осталось без адреса. Адрес
устроен по-разному там, где по-разному устроен источник:

| Формат | Адрес | Откуда берётся |
|---|---|---|
| PDF | `стр. N` | номер страницы есть в самом файле — адрес точный |
| `.docx` | `стр. N · абз. M` | номер абзаца (блока) в документном порядке; страница — по последней отрисовке Word (`w:lastRenderedPageBreak`, явные `w:br w:type="page"`), у файлов без таких отметок остаётся только абзац |
| `.docx`, таблица | `… · абз. M · яч. 3:2` | строка и колонка клетки; вложенная таблица дописывается путём — `яч. 3:2/1:4` |
| `.xlsx` | `ТЗ!B7` | имя листа и адрес клетки A1 |

Отчёт печатает сводку по пакету, вердикт и — с `--with-text` — список фрагментов
(строки таблиц показываются по клеткам, как их увидит значение). Код 1
означает, что нашёлся фрагмент или значение без адреса: это дыра в парсере
формата, а не свойство документа, и оставаться незамеченной она не должна.

`metric` (P1.7) замеряет критерий PoC H1 — «доля документов комплектов,
пригодных для проверок после парсинга» (порог ≥ 80 %). Команда обходит пакет
из `--input-dir`, разбирает каждый поддерживаемый документ парсером его
формата и печатает долю успешных разборов: знаменатель — все поддерживаемые
файлы обхода (файл, который сканер отметил проблемным, считается неудачей без
попытки разбора), успех — разбор без ошибки. Отчёт показывает общий процент
против порога, вердикт, разбивку по форматам и список неразобранных файлов с
причинами; `--format json` отдаёт те же данные машиночитаемо. Справочный
счётчик «с потерями» (docx/xlsx) на H1 не влияет: потеря содержимого — не
провал разбора, а у PDF потери не измеряются вовсе (отчёт помечает это явно,
а не показывает ноль). Порог сравнивается с неокруглённой долей: 79,96 % не
проходят как «80,0». Пакет без поддерживаемых документов — не провал: метрика
не определена, команда сообщает «нечего измерять» и выходит с кодом 0.
Ожидаемый результат — сводка вида:

```text
Каталог: ./docs/ТЭК СПб сервис WAF
Файлов: 29, поддерживаемых 29, прочих 0
Разобрано успешно: 29 из 29 — H1 100.0 % (порог 80 %)
С потерями: 0 (docx/xlsx); у PDF потери не измеряются
Вердикт: порог 80 % достигнут
```

Коды выхода:

| Код | Значение |
|---|---|
| 0 | замечаний нет (для `extract-reqs` — карточки построены и у каждого значения есть адрес; подозрительные значения помечены `✗`, но кода не касаются; для `trace` — трассируемость полная; для `metric` — порог H1 ≥ 80 % достигнут или поддерживаемых документов в пакете нет; для `dump-docs` — `docs.json` записан и все поддерживаемые документы разобраны) |
| 1 | есть замечания: проблемные файлы (см. «Замечания»/«Ошибки разбора» отчёта), потери при извлечении или фрагменты и значения без адреса в источнике (`trace`, `extract-reqs`); у `metric` — H1 ниже порога 80 %; у `dump-docs` — поддерживаемый документ не разобран (в его записи `note` и `failed`, файл при этом записан) либо `docs.json` не удалось создать |
| 2 | ошибка в аргументах (не задан вход, неизвестные `--command`/`--format`, лишние аргументы, `--output-dir` не у `dump-docs` или, наоборот, не задан для него, `--file`/`--with-text` вместе с `dump-docs` или `metric`, не задан `--input-dir` для `metric`) |
| 3 | неверный путь (каталога нет или это не каталог) |

## Сборка и тестирование

```bash
# сборка бинарника
go build -o bin/tenderguy ./cmd/tenderguy
./bin/tenderguy --input-dir ./docs

# проверка сборки всего модуля
go build ./...

# тесты (table-driven, с race-детектором)
go test -race ./...

# линтер
golangci-lint run
```

Тесты `parse-pdf` не зависят от документов заказчика: PDF-фикстуры (типовая
страница с текстовым слоем и «скан» без него) лежат в исходниках base64 и
генерируются на месте во временный каталог. Для OCR-теста в системе должны быть
установлены poppler и tesseract с русским пакетом (см. «Требования»).
Тесты `parse-xlsx` тоже самодостаточны: книги Excel собираются кодом excelize
прямо в тестовом каталоге — среди них синтетическая «спецификация», повторяющая
структуру файлов НЭО (широкий лист слияниями и формулами + скрытый справочник
ОКПД2 на 256 строк).

Тесты `extract-reqs` не читают документы заказчика: контрольные примеры ИНН,
КПП, ОГРН и сумм посчитаны в самих тестах (для ИНН/ОГРН — по методикам ФНС,
поэтому тест падает, если изменится алгоритм проверки, а не если изменится
заявка), а текстовые карточки собираются из фикстур `parse-docx`/`parse-xlsx`.

Тесты `trace` тоже самодостаточны: адреса проверяются на тех же синтетических
`.docx`, книгах `.xlsx` и base64-фикстурах PDF. Отдельный тест
(`TestEveryFragmentHasAddress`) утверждает главное свойство P1.6 — у каждого
фрагмента с содержимым есть адрес, — по всем трём форматам сразу; он падает,
если новый формат или новый вид элемента парсера отдаст содержимое без
координат.
