# mvp.md — Эпики разработки MVP (минимальный функционал)

**Источник:** `issues.md` (эпики E0–E8), `analyze.md` (раздел 8 «Границы MVP этапа 1»)
**Роль:** senior system & business analyst
**Дата:** 10.11.2026
**Статус:** v0.1 — границы MVP к утверждению заказчиком

> Принцип среза: MVP — это **один сквозной сценарий**: специалист загружает закупочную документацию и подготовленный пакет заявки → система находит дефекты → специалист получает отчёт с источниками и подтверждает его перед подачей. Всё, что не работает на этот сценарий, вырезано. Детализация до задач TND-xxx — после утверждения среза (согласно принятому порядку).

---

## Целевой результат MVP (единственный критерий успеха)

На ≥3 реальных заявках по каждому из трёх пилотных заказчиков система находит заранее согласованный набор классов дефектов (реквизиты, сроки «свежести», состав пакета) с recall ≥ 0,90 по блокирующим классам на golden set, каждое замечание — с цитатой-источником, финальное решение — за специалистом.

## Состав MVP: эпики и минимальный срез

| Эпик из issues.md | В MVP? | Минимальный срез | Что вырезано из эпика |
|---|---|---|---|
| **E0** Discovery и spikes | ✅ частично | Spike A (парсинг), Spike C (модель/контур), инвентаризация исторических данных, каталог классов дефектов, baseline-метрики, решение ИБ по контуру | Воркшопы в полном объёме, Spike B (данные площадок — не нужен: загрузка ручная), юридическая экспертиза ЭТП |
| **E1** Инфраструктура и ИБ | ✅ минимально | Один контур (по решению ИБ из E0), абстракция LLM-провайдера, файловое хранилище, одна роль «специалист» + журнал доступа, окружение dev/prod | SSO, много окружений, полная ролевая модель, политика ретеншена (кроме базового удаления), мониторинг нагрузки |
| **E2** Инженерия документов | ✅ | Ручная загрузка (архив/файлы: DOCX, PDF, XLSX, сканы), извлечение текста и таблиц, карточки документов с атрибутами (ИНН, КПП, ОГРН, даты, суммы), ссылка на фрагмент-источник | OCR высокого качества для рукописных фрагментов, версионирование редакций документации с diff (TND-027), XML ЭДО |
| **E3** Движок проверок | ✅ ядро | Уровень 1 (детерминированные проверки): состав пакета, сверка реквизитов с мастер-данными, сроки «свежести», номера закупки; уровень 2 частично: форма ↔ инструкция; уровень 3 (LLM) — только по 2–3 утверждённым семантическим классам, с confidence и статусом «требует подтверждения» | Арифметика цен/НДС сверх базовой, сверка ТЗ/спецификации с «дотендерной» версией, коллизии извещение↔документация↔договор, проверки «упаковки», профили «дотошности», сравнение прогонов |
| **E4** База знаний, правила, мастер-данные | ✅ минимально | Реестр правил (версионируемый, владелец назначен) под каталог дефектов MVP; правила «свежести» как данные; мастер-данные: карточка(и) юр. лица, лицензии/сертификаты, реестр справок со сроками; нормативная база — только Положения о закупке трёх заказчиков + базовые нормы 223-ФЗ | Полный корпус 44-ФЗ/подзаконных актов/практики ФАС, многоступенчатое наследование правил (MVP: базовый слой + профиль заказчика), алерты об истечении справок |
| **E5** Golden set и качество | ✅ обязательный гейт | Разметка имеющихся «косячных» заявок с причинами отклонения + 3–5 выигранных комплектов ТЭК СПб; метрики recall/precision/трассируемость; пороги утверждены до старта E3; ручной регрессионный прогон перед релизом | Регрессия в CI на каждое изменение, canary-выкатка, продуктовые метрики принятия в полном объёме |

| **E8** Тиражирование и эксплуатация | ❌ | — | Весь эпик (регламент обновления БЗ — минимальная инструкция владельцу правил, без автоматизации) |

## Порядок разработки MVP

```
E0-min (spikes + каталог дефектов + решение ИБ)
   │
   ├─► E1-min (контур) ─► E2-min (загрузка и парсинг)
   │                              │
   └─► E4-min (правила +          │
        мастер-данные) ───────────┤
   │                              ▼
   └─► E5-min (golden set, ──► E3-min (движок проверок) ──► E6-min (отчёт + sign-off)
        пороги — ГЕЙТ)
```

Обязательная последовательность:
1. **E0-min** — без него не фиксируются ни контур, ни классы дефектов (входные гейты по AR-2, AR-8, AR-15).
2. **E5-min до E3-min** — утверждённые пороги качества являются входным гейтом разработки движка (решение из `issues.md`, примечание 2).
3. E1/E2/E4 могут идти параллельно после E0; E6 — после первого работающего среза E3.

## Явно вне MVP (зафиксировано против расползания скоупа — AR-22)

- Любые интеграции: ЭТП, ЕИС, ФНС, Госуслуги, банк/казначейство, 1С/СЭД.
- Мониторинг закупок по ИНН заказчиков.
- Генерация/автозаполнение документов, сборка архива заявки.
- Подписание ЭП и подача заявки.
- Проверки контрагента/заказчика (РНП, арбитраж, банкротство).
- Fine-tuning моделей.
- Мультитенантность и внешние пользователи.
- Диалоговый Q&A-режим.

Изменение этого списка — только через change request.

## Минимальные метрики приёмки MVP

| Метрика | Порог | Источник |
|---|---|---|
| Recall по блокирующим классам дефектов (golden set) | ≥ 0,90 | analyze.md, раздел 9 |
| Precision (доля подтверждённых замечаний) | ≥ 0,80 | analyze.md, раздел 9 |
| Трассируемость (замечание → фрагмент-источник) | 100 % | analyze.md, раздел 9 |
| Воспроизводимость (расхождение повторных прогонов) | ≤ 5 % | analyze.md, раздел 9 |
| Сквозной сценарий пройден на реальных заявках | ≥ 3 на каждого из 3 заказчиков | настоящий документ |
| Sign-off специалиста | обязателен до подачи, архитектурно | ASM-8, AR-16 |

Время проверки и стоимость инференса — фиксируются как baseline по итогам MVP (целевые пороги требуют данных P0-2, которых пока нет).

## Открытые вопросы, блокирующие фиксацию среза MVP

Минимальный набор из P0, на который нужны ответы **до старта** (остальные P0 — до полного ТЗ v1.0):

1. **P0-6** — контур и допустимость внешнего LLM API (блокирует E1-min целиком).
2. **P0-9** — что реально есть в исторических данных и есть ли протоколы отклонений (блокирует E5-min — гейт).
3. **P0-10** — от скольких юр. лиц подаются заявки (объём мастер-данных E4-min).
4. **P0-4** — правовые режимы трёх заказчиков и доступ к их Положениям о закупке (состав БЗ E4-min).
5. **P1-13** — подтверждение закрытого перечня классов дефектов MVP (объём E3-min).
6. **P1-18** — формат выгрузки отчёта (E6-min, один формат).
