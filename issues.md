## E0 — Discovery, обследование и spikes

**Цель:** снять критические пробелы `tz.md` (G1–G14) и получить основания для проектирования, оценки и фиксации границ MVP.

**Входит:**
- Воркшоп №1 «Процесс и цели»: замер as-is, baseline-метрики (время на заявку, отклонения и их причины), роли, ответы на P0-1…P0-3, P0-10, P0-12.
- Воркшоп №2 «Дефекты и правила»: закрытый каталог классов дефектов (P1-13), разбор 2–3 реальных отклонений по шагам, черновик реестра правил.
- Юридическая и ИБ-экспертиза: категорирование данных (КТ/ПДн), допустимость внешнего LLM API, допустимость автоматизированного доступа к ЭТП (A12, A13, AR-8).
- Spike A (TND-010) — парсинг: 3 реальных комплекта документации, измерение качества извлечения текста/таблиц/атрибутов.
- Spike B (TND-011) — данные площадок: что легитимно доступно по трём заказчикам (извещения, протоколы, причины отклонений).
- Spike C (TND-013) — модель и контур: бенчмарк ≥2 моделей на реальных документах, стоимость и время инференса.
- Инвентаризация исторических данных (TND-007): выигранные комплекты по ТЭК СПб, «косячные» заявки с версиями, наличие протоколов отклонений.
- **Статус инвентаризации на 2026-11-16:** документация НЭО восстановлена — 8 файлов с повреждёнными кодировкой именами переименованы (содержимое не менялось, размеры совпали побайтово), структура папок приведена к приложениям 1–3 (Приложение 1_ТЗ, Приложение 2_Проект договора, Приложение 3 РЭО); по НЭО собрана полная пара «закупочная документация + заявка». Каталог закупочной документации ТЭК СПб пуст, по ТГК-1 — 0 файлов; протоколы исходов и «косячные» версии заявок отсутствуют (подробности — раздел «Статус данных на 2026-11-16» в конце документа).
- Формализация ТЗ v1.0: цели, границы, ФТ/НФТ, критерии приёмки.

**Не входит:** любая продуктовая разработка; сбор персональных учётных данных площадок.

**Критерии готовности:**
1. Подписаны ответы на все вопросы P0 (`analyze.md`, раздел 6).
2. Три spike завершены с письменными заключениями и go/no-go по соответствующим рискам (AR-2, AR-5, AR-20).
3. Утверждён каталог классов дефектов MVP с приоритетами.
4. Выпущено ТЗ v1.0 с измеримыми критериями приёмки и целевыми метриками (раздел 9 `analyze.md`).
5. Назначен владелец правил и базы знаний (P0-7).

**Риски эпика:** AR-15 (данные недоступны/непригодны), AR-22 (размытие скоупа).

**Трассировка к tz.md:** весь документ; в особенности п. «Что мб полезно для обучения агента» 1–4.

## E1 — Инфраструктура, ИБ-контур и платформа

**Цель:** обеспечить технологический фундамент, удовлетворяющий ограничениям ИБ и правового режима, определённым в E0.

**Входит:**
- Выбор и развёртывание контура: on-prem / российское облако / внешний LLM API — по итогам P0-6 и Spike C.
- Абстракция LLM-провайдера (TND-050): переносимость между моделями, pin версий (AR-20, AR-12).
- Хранилище документов и версионирование файлов; файловый архив с контролем целостности.
- Ролевая модель, аутентификация (SSO при необходимости), журналирование и аудит доступа (P1-23).
- Категорирование данных, маскирование/анонимизация перед отправкой во внешние сервисы (если внешний API разрешён).
- CI/CD, окружения dev/stage/prod, мониторинг и логирование.
- Политика ретеншена и удаления документов (P2-34).

**Не входит:** интеграции с ЭТП, ЕИС, ФНС, Госуслугами, банком (проверяются spike'ами, в MVP — ручной импорт); криптографический контур подписания ЭП (этап 2, AR-7).

**Критерии готовности:**
1. Контур развёрнут, соответствует заключению ИБ из E0.
2. Смена модели/провайдера возможна конфигурацией, без изменения кода проверок.
3. Аудит-журнал фиксирует все обращения к документам с КТ.
4. Нагрузка (объёмы из P0-2) подтверждена тестом производительности.

**Риски эпика:** AR-8, AR-11, AR-12.

**Трассировка к tz.md:** п. 1 «Дать доступы к площадкам… по части безопасности» (опровержение ложной предпосылки A13).

## E2 — Инженерия документов: загрузка, парсинг, нормализация

**Цель:** превратить разнородный вход (закупочная документация + подготовленный пакет заявки) в структурированные машиночитаемые сущности. Это основной источник ошибок (AR-2), поэтому — отдельный эпик с собственными метриками качества.

**Входит:**
- Ручная загрузка: архивом и отдельными файлами (DOCX/PDF/XLSX/сканы/XML) — MVP-контур по ASM-6.
- Слой нормализации: извлечение текста, OCR сканов, извлечение таблиц, пагинация, привязка фрагментов к координатам в исходнике (для трассируемости замечаний).
- Классификация документов и построение карточек: тип документа, реквизиты, даты, принадлежность к закупке/лоту/форме.
- **Добавлено 2026-11-16:** парсинг инструкций из ЗД ЭФ (`226717 ЗД ЭФ (К, КП, ЗП).docx`, НЭО): извлечение требуемого состава пакета, пар «форма ↔ инструкция по заполнению», требований к участнику (лицензии, квалификация, штат, обеспечение).
- Извлечение атрибутов для детерминированных проверок: ИНН, КПП, ОГРН, наименования, адреса, суммы, даты выдачи/окончания.
- Версионирование редакций закупочной документации с diff и перезапуском проверок (TND-027, AR-13).
- Метрика качества парсинга в карточке документа; ветка ручной верификации при низкой уверенности.

**Не входит:** автоматическая загрузка с ЭТП/из ЕИС и мониторинг закупок (spike B, за скоупом MVP); извлечение требований в реестр (E4).

**Критерии готовности:**
1. На выборке из ≥5 реальных комплектов трёх заказчиков доля документов, корректно классифицированных и разобранного текста которых достаточно для проверок, ≥ целевой (определяется в E0 по итогам Spike A).
2. Каждый извлечённый фрагмент имеет ссылку «документ + страница/пункт» (100 % трассируемость).
3. Новая редакция документации автоматически детектируется и запускает diff + перезапуск проверок.

**Риски эпика:** AR-2, AR-13, AR-19.

**Трассировка к tz.md:** п. 2.a (сверка ТЗ и спецификации — входные данные), п. 3.a–c (состав, формы, содержание — источник требований к парсингу).

## E3 — Движок проверок

**Цель:** ядро этапа 1. Гибридная архитектура по AR-1: детерминированные правила → структурное сопоставление → LLM только для семантики. Позиционирование — decision support с обязательным подтверждением человеком (AR-16, ASM-8).

**Входит:**
- **Уровень 1 — детерминированные проверки:** состав пакета против реестра требований (добавлено 2026-11-16: проверка 3a — состав пакета против требований ЗД ЭФ на данных НЭО; для ТЭК СПб — состав по описи); сверка реквизитов с мастер-данными (юр. адрес, КПП, наименования — заявленная боль); сроки действия и «свежесть» справок; арифметика (цены, НДС, обеспечение); номера закупки/лота.
- **Уровень 2 — структурное сопоставление:** форма ↔ инструкция по заполнению (добавлено 2026-11-16: проверка 3b — инструкции извлечены из ЗД ЭФ НЭО, ~90 упоминаний; сверка выполняется по пакету НЭО); тендерное ТЗ/спецификация ↔ «дотендерная» версия (ключ сверки — из P1-16); извещение ↔ документация ↔ формы ↔ проект договора с правилом обработки коллизий (P1-19); проверки «упаковки» заявки (P1-17).
- **Уровень 3 — семантические проверки (LLM):** соответствие содержания заполненной формы сути требования; каждый вывод — цитата-источник, confidence, статус «требует подтверждения человеком»; ветка «инструкция не найдена» → эскалация (A9).
- Трёхуровневое наследование правил: базовый нормативный слой → профиль заказчика → профиль процедуры (AR-17).
- Шкала критичности замечаний: блокирующее / предупреждение (P2-26).
- Повторный прогон после правок, сравнение прогонов, статусы устранения замечаний (P2-29).

**Не входит:** генерация и автозаполнение документов (E7); проверки контрагента/заказчика — РНП, арбитраж, банкротство (P1-24, за скоупом MVP); подписание ЭП и подача (E7).

**Критерии готовности:**
1. Покрыты все утверждённые в E0 классы дефектов MVP.
2. Метрики качества (E5) достигают целевых порогов: recall ≥ 0,90 по блокирующим классам, precision ≥ 0,80, воспроизводимость ≤ 5 % расхождений между прогонами.
3. 100 % замечаний имеют источник-цитату и severity.
4. Автоподача/автоисправление документов невозможны архитектурно (запрет этапа 1).

**Риски эпика:** AR-1, AR-21, AR-14.

**Трассировка к tz.md:** п. 1 (анализ рисков участия), п. 3.a–c (трёхкратная проверка пакета — прямое ядро эпика).

## E4 — База знаний, правила и мастер-данные

**Цель:** формализовать экспертизу, которая сейчас «в голове» специалиста и в личном архиве версий (AR-3), и обеспечить систему нормативной базой. «Обучение агента» из `tz.md` реализуется как RAG + реестр правил, а не fine-tuning (ASM-4).

**Входит:**
- Реестр декларативных правил с версионированием, владельцем и changelog; правило «документ × заказчик × режим → срок свежести» как данные, не код (A11).
- **Добавлено 2026-11-16:** правила сверки ТЗ и спецификаций (шаг 2a tz.md): позиции закупки (ТЗ ред. 19.10.2026, спецификации ТЕХ/КОММ, коды ОКПД2 — `Приложение 1_ТЗ/` НЭО) ↔ позиции заявки (`15Спецификация техническая часть.xlsx`, `16Спецификация (Коммерческое предложение…).xlsx`) — как данные, с ключом сверки по позиции/ОКПД2.
- База знаний нормативки (TND-020-контекст): 44-ФЗ, 223-ФЗ, подзаконные акты, Положения о закупке трёх заказчиков — с датой среза и версионированием (AR-4).
- Профили трёх заказчиков (АО «НЭО», ПАО «ТГК-1», АО «ТЭК СПб»): специфические требования, «уровень дотошности», история отклонений.
- Мастер-данные поставщика: карточки юр. лиц (возможная множественность — A3, P0-10), лицензии, сертификаты, СРО, статусы производителя, штатные единицы, финансовые показатели, архив справок со сроками и алертами об истечении.
- Доменная модель (TND-020): Закупка → Редакция → Заявка → Документ → Требование → Правило → Проверка → Замечание → Мастер-данные (AR-10 — фундамент и для этапа 2).
- Каталог требуемых справок с чек-листом и контролем сроков (замена автополучения из ФНС/Госуслуг — AR-6).

**Не входит:** автополучение справок из внешних сервисов (spike, P3-38); интеграция с 1С/СЭД (P1-22 — по итогам приоритизации); fine-tuning моделей (P3-42).

**Критерии готовности:**
1. Правила извлекаются из экспертизы и истории отклонений, версионируются, имеют владельца (P0-7 назначен).
2. База знаний привязана к дате среза; каждое замечание ссылается на версию документа-основания.
3. Мастер-данные заведены по всем юр. лицам поставщика; проверка реквизитов работает против них.
4. Профили трёх пилотных заказчиков заполнены и проверены на исторических кейсах.

**Риски эпика:** AR-3, AR-4, AR-17, AR-18.

**Трассировка к tz.md:** п. 1.a–f (требования к исполнителю), п. 2.b (справки), «обучение агента» п. 2 и п. 4 (законодательство).

## E5 — Golden set и контур оценки качества

**Цель:** сделать качество измеримым и доказать готовность системы (AR-9). Входной гейт разработки E3: без утверждённых порогов движок не начинается.

**Входит:**
- Инвентаризация и разметка исторических заявок (TND-014): «косячные» заявки с версиями + протоколы/письма с причинами отклонения; выигранные комплекты по ТЭК СПб — с экспертной разметкой корректности (A14, A15).
- Формирование golden set: покрытые классы дефектов, фиксация эталонных ответов, версионирование набора. **Уточнение 2026-11-16:** в PoC-Min используется мини-эталон, а не полный golden set — разовая ручная разметка имеющихся пакетов (исходная оценка 5–10 пакетов; фактически доступно 2 — НЭО и ТЭК СПб, см. `poc.md`, эпик P0).
- Утверждение метрик и порогов (раздел 9 `analyze.md`) с заказчиком до старта E3.
- Регрессионный прогон в CI при каждом изменении правил/промптов/модели (AR-12); canary-выкатка и откат.
- Сбор обратной связи «принято/отклонено замечание» как источник тюнинга порогов (AR-21) и продуктовых метрик принятия.

**Не входит:** разметка данных под fine-tuning (не планируется — ASM-4, P3-42).

**Критерии готовности:**
1. Golden set содержит ≥ N размеченных кейсов по каждому классу дефектов (N — из E0), включая реальные отклонения с документально зафиксированной причиной.
2. Метрики и пороги утверждены заказчиком письменно.
3. Регрессия golden set блокирует релиз при любом падении recall/precision.

**Риски эпика:** AR-9, AR-15 (если протоколы отклонений не сохранились — запрос из ЕИС/ЭТП).

**Трассировка к tz.md:** «обучение агента» п. 3 («косячные заявки… перепроверить что найдёт ИИ и что нашли мы» — прямая формулировка задачи эпика).

## E6 — Отчёт о проверке и рабочее место специалиста

**Цель:** довести результат проверок до пользователя так, чтобы система была принята (AR-14): ни недоверия, ни слепого доверия.

**Входит:**
- Отчёт о проверке: замечания с severity, категорией, цитатой-источником, рекомендацией; фильтры; переход к фрагменту документа.
- Статусы замечаний и workflow устранения; повторная проверка после правок; история проверок и сравнение прогонов (P2-29).
- Обязательный human sign-off перед подачей; дисклеймер о границах ответственности (AR-16).
- Формат выгрузки по итогам P1-18 (веб-отчёт / PDF / XLSX-чек-лист — определить в E0).
- Чек-лист организационных вопросов: доступы и аккредитация на площадке, тариф, наличие средств для обеспечения заявки/исполнения — MVP как чек-лист с ручным заполнением (A7).
- Уведомления: завершение проверки, новая редакция документации, приближение срока подачи, истекающие справки (P2-30).
- Дашборд руководителя: число заявок, время, дефекты по классам, доля принятых замечаний (P2-31).
- Обучение пилотной группы, инструкции, сбор обратной связи (P2-33).

**Не входит:** интеграция с банком/казначейством для контроля остатков (P3-37, этап 2); диалоговый Q&A-режим (P2-27 — по итогам приоритизации).

**Критерии готовности:**
1. Пилотная группа провела через систему ≥ M реальных заявок (M — из E0) без возврата к «проверке в папках».
2. Доля замечаний, принятых без правок, ≥ целевой; метрика ведётся.
3. Ни одна заявка не может быть подана без явного sign-off специалиста в системе.

**Риски эпика:** AR-14, AR-21.

**Трассировка к tz.md:** п. 2.c (доступы/тариф/обеспечение), п. 3 (многократная проверка — UX повторных прогонов), проблематика (экономия времени).

## E7 — Автоматизация подготовки заявки (этап 2)

**Цель:** сократить время подготовки пакета, а не только проверки. Целевой уровень автоматизации фиксируется в E0 (P3-35): подсказки → автозаполнение → генерация → сборка → подписание → подача. По ASM-5 подписание и подача — за скоупом до отдельного решения.

**Входит (состав уточняется после приёмки этапа 1):**
- Библиотека шаблонов форм по заказчикам с версионированием (P3-36).
- Автозаполнение форм из мастер-данных поставщика (реквизиты, лицензии, показатели — E4 как фундамент).
- Генерация сопутствующих документов: декларации, письма, описи.
- Сборка комплекта заявки: структура архива, именование, опись, требования площадки.
- Сверка ТЗ/спецификации с автопредложением исправлений (развитие проверки из E3).
- Spike и, при реализуемости, модуль подписания ЭП (AR-7: КриптоПро, токены, МЧД — только после отдельного spike и юр. экспертизы).
- Spike по автополучению справок ФНС/Госуслуги/ЕИС (P3-38, AR-6) — решение по итогам.
- Мониторинг новых закупок по ИНН трёх заказчиков и автозаведение в работу (P3-39) — только легитимными каналами по итогам Spike B.
- Контроль обеспечения заявки/исполнения: интеграция с банком/казначейством, учёт независимых гарантий (P3-37).
- Генерация запроса разъяснений / протокола разногласий по коллизиям, найденным E3 (P3-43).

**Не входит:** полная автономная подача заявки без человека (не рассматривается на горизонте планирования).

**Критерии готовности (эпик запускается только при):**
1. Этап 1 (E1–E6) принят по метрикам.
2. Целевой уровень автоматизации утверждён заказчиком (P3-35).
3. Spikes по ЭП, справкам и ЭТП дали положительные заключения (технические и юридические).

**Риски эпика:** AR-5, AR-6, AR-7, AR-22.

**Трассировка к tz.md:** п. 2 (этап 2 — «автоматизация подготовки заявки»), п. 2.b–d, «обучение агента» п. 1 (доступы к площадкам).

## E8 — Тиражирование, эксплуатация и развитие

**Цель:** система не деградирует после внедрения (AR-4, G12) и может масштабироваться за пределы трёх заказчиков.

**Входит:**
- Регламент эксплуатации: владелец базы знаний, порядок обновления нормативки и Положений о закупке, мониторинг возраста индекса БЗ, алерты.
- Мониторинг качества в проде: деградация метрик, дрейф модели, бюджет на токены и стоимость проверки одной заявки (AR-11).
- Поддержка: SLA, обработка инцидентов «система пропустила дефект» с разбором и добавлением кейса в golden set.
- Тиражирование: подключение новых заказчиков через механизм профилей (E4); оценка мультитенантности и продуктовой модели по ответу P0-3.
- Аналитика рисков участия (go/no-go), оценка НМЦД, прогноз вероятности победы (P3-40) — как направление развития.

**Не входит:** продажа решения внешним клиентам — до отдельного стратегического решения (P3-41).

**Критерии готовности:**
1. Регламент обновления БЗ действует; средний возраст нормативной базы в индексе не превышает установленного порога.
2. Новый заказчик подключается настройкой профиля без изменения кода движка.
3. Главная бизнес-метрика — число отклонений заявок после внедрения — отслеживается и снижается относительно baseline из E0.

**Риски эпика:** AR-4, AR-12.

**Трассировка к tz.md:** проблематика (долгосрочная экономия времени), скоуп заказчиков (потенциал расширения).
