## A. Дефекты кода: подтверждены прогоном, требуют задачи

### A1. NFD-имена файлов ломают сопоставление состава → ложное блокирующее замечание

- **Источник:** PR #72, находка 1. Воспроизведено повторно 2026-11-24 на влитом
  коде (связка P2.8 → P2.4).
- **Где:** `internal/rules/classcomp.go`, `normalizeFileName` / `matchComposition`.
- **Суть:** в пакете заявки 6 файлов из 46 хранятся с decomposed-именами
  (архивы с macOS): буква «й» лежит как `и` + U+0306. Паттерн, извлечённый из
  закупочной документации, приходит в NFC, `filepath.Match` сравнивает байты —
  совпадения нет.
- **Доказательство:** пункт `zd-08` («Одобрение … сделки», паттерн
  `*Одобрение крупной сделки*`) даёт `статус: нет` и блокирующее замечание
  «нет документа в составе», хотя файл физически присутствует в подкаталоге
  «Правоустанавливающие документы». Из 18 блокирующих замечаний прогона по
  заявке как минимум одно — этот дефект.
- **Как воспроизвести:** обход `docs/…/Заявка` с проверкой
  `unicodedata.normalize('NFC', name) != name` (7 имён во всём `docs`, 6 в заявке),
  затем `extract-zd --emit composition` → конфиг → `check --input-dir <заявка>`.
- **Предлагается:** NFC-нормализация имени файла и паттерна в `matchComposition`
  плюс регрессионный тест на NFD-имени (фикстура — имя файла собирается из рун
  с комбинируемым диакритиком). `golang.org/x/text` уже присутствует в `go.sum`
  как indirect — переход в прямые зависимости нужно зафиксировать осознанно
  (правила проекта требуют явного списка библиотек).
- **Влияние:** высокое. Ложное блокирующее = «пакет нельзя подавать» при
  корректном пакете.

### A2. Матчер состава знает только basename — подкаталог нельзя прикрыть пунктом

- **Источник:** PR #72, находка 3. Подтверждено: 28 предупреждений «файл не
  сопоставлен ни с одним пунктом требуемого состава» в прогоне по заявке.
- **Где:** `internal/rules/classcomp.go`, ветка `matchByFilename`.
- **Суть:** подкаталог с подтверждающими документами (27 файлов с произвольными
  именами: договоры, акты, счета, УПД) сопоставляется с пунктами состава по имени
  файла, поэтому либо каждый файл нужен отдельным пунктом, либо все 27 остаются
  «неожиданными».
- **Предлагается:** способ сопоставления по относительному пути (префикс
  подкаталога или glob по пути), например `match.by = "path"` с паттерном
  `Опыт/*`; либо пункт состава с явной семантикой «любое количество файлов в
  подкаталоге X». Решение влияет на формат конфига — согласовать до реализации.
- **Влияние:** среднее. Шум в отчёте, который приучает специалиста игнорировать
  предупреждения.

### A3. Консистентность реквизитов без `orgs` тонет в реквизитах контрагентов

- **Источник:** PR #72, находка 2.
- **Где:** `internal/rules/classreqs.go` (группы сверки внутренней консистентности).
- **Суть:** реквизиты контрагентов из подкаталога опыта (договоры, УПД, счета)
  попадают в те же группы сверки, что реквизиты участника. При пустом разделе
  `orgs` предупреждения «ИНН/КПП/ОГРН различаются» перечисляют десятки
  легитимных чужих значений.
- **Предлагается:** скоупинг «реквизиты участника vs прочие» — через `orgs`
  (эталон задаёт участника, всё остальное вне сверки) или через привязку к
  пункту состава (документы опыта не участвуют в консистентности участника).
  Калибруется разметкой, поэтому делать после получения разметки мини-эталона.
- **Влияние:** высокое для полезности класса `reqs` на реальных данных: сейчас
  класс на реальном пакете выдаёт шум вместо сигнала.

### A4. Детектор достоверности пагинации не применён в `check` — адреса могут уводить не туда

- **Источник:** пропущено в процессе реализации P2.8 (детектор построен только
  внутри `internal/zd`).
- **Где:** `internal/parser` (поле `Block.Page` / `Ref.Page`), потребители —
  классы P2.3–P2.5 и `writeCheckText`/`writeCheckMarkdown`.
- **Суть:** пагинация `.docx` — свойство последней отрисовки Word, а не файла.
  Замер по реальным данным: в закупочной документации 460 блоков помечены
  «стр. 2» при максимуме 41 и оглавлении до стр. 45; в коротких файлах заявки все
  блоки помечены «стр. 1». `extract-zd` это обнаруживает и страницы в адреса не
  включает, а `check` — печатает как есть.
- **Доказательство:** в прогоне `check` по заявке 3 адреса из 49 несут страницу
  `.docx` (например `…docx · стр. 4 · абз. 58`), при этом у других файлов того же
  пакета все блоки помечены одной страницей — то есть значение недостоверно.
- **Предлагается:** вынести детектор из `internal/zd` в общий слой
  (`internal/parser` или `internal/trace`), применять ко всем классам правил и к
  отчёту: `Page` включать в адрес только при `trusted`, иначе печатать причину
  недостоверности в примечании отчёта. Контракт адрес-лестницы из P2.8 при этом
  становится общим для всего движка.
- **Влияние:** высокое. Недостоверный адрес хуже отсутствующего: он выглядит
  валидным и уводит специалиста не туда (прямое требование владельца —
  проектировать под худший сценарий входа).

### A5. OCR-мусор в наименованиях организаций из сканов

- **Источник:** PR #72, находка 4.
- **Где:** `internal/reqs` (извлечение `org_name` из текста OCR) поверх
  `internal/parser/pdf.go`.
- **Суть:** из сканов второго пакета извлекаются фрагменты фраз как
  «наименование организации».
- **Предлагается:** не чинить точечно, а включить в контур оценки precision
  (E5, golden set) — сейчас нечем измерить, стало ли лучше.
- **Влияние:** низкое сейчас (реквизиты без `orgs` и так в режиме
  консистентности), вырастет при включении семантических проверок.

## B. Вопросы трактовки: решение за человеком, кода не требуют до решения

### B1. Применимость пунктов требуемого состава (18 блокирующих по заявке)

Таблица «Структура заявки» в закупочной документации перечисляет документы на все
случаи: иностранное юрлицо, разрешение миграционной службы, копия паспорта, ИНН
физлица, СНИЛС, сводная таблица стоимости работ/услуг, планы привлечения
субподрядчиков и распределения объёмов коллективного участника, гарантийное
письмо аккредитованного поставщика. `extract-zd` ставит `required=true`, когда в
тексте пункта нет явного маркера условности («предоставляется только в случае…»,
«не требуется предоставлять…», «не является обязательной», «является
рекомендуемой», «по мнению Участника»); в таблице таких маркеров у перечисленных
пунктов нет.

Итог прогона: 18 блокирующих «нет документа в составе», из них 1 — дефект A1,
остальные — документы, неприменимые к данному участнику или способу закупки.

**Варианты:** (а) слой применимости — данные из Извещения/ТЗ (тип участника,
предмет: товар/работы/услуги) автоматически снимают неприменимые пункты;
(б) явная отметка человека в конфиге (`required: false` или новое поле
`applicable_if`); (в) понизить уровень замечания для пунктов без маркера
условности до warning. Решение влияет на то, можно ли считать блокирующие
замечания сигналом к действию.

### B2. Один блок инструкций на несколько форм — статус `shared`

В разделе образцов форм один блок «Инструкции по заполнению» обслуживает
несколько идущих подряд форм (в реальном документе 2 такие группы, 4 формы).
Сейчас все формы группы получают `instruction_status: shared`, один и тот же
набор пунктов инструкции и одно отклонение с адресами всех участников группы.

**Вопрос к P3 (#4):** если семантическая сверка будет проверять форму по её
инструкции, `shared` означает «сверяй с несколькими вариантами формы» — это
контракт входа P3. Альтернатива: не привязывать инструкцию вовсе и эскалировать
как отклонение структуры.

### B3. Форма из двух частей с двумя блоками инструкций

В реальном документе есть окно формы, содержащее два блока «Инструкции по
заполнению» (форма из двух частей). Сейчас привязывается первый блок, второй
остаётся видимым в составе пунктов инструкции. Формально это отклонение структуры
документа; трактовка не утверждена.

### B4. История коммитов

Коммит P2.8 (`3dc46f3`) влит без трейлера `Co-authored-by: Qwen-Coder`, который
присутствует в коммитах P2.4/P2.5/P2.7. Причина: гейт проекта блокирует
`git commit --amend` (переписывание истории — только человек). Теперь коммит в
`main`, правка возможна только переписыванием истории — вероятно, не стоит того;
зафиксировано как расхождение стиля.

## E. Блокеры, которые снимает только человек (данные)

1. **Разметка мини-эталона:** дефекты обоих пакетов с привязкой к классу и
   фрагменту. Без неё recall ≥ 0,90 неизмерим, а #64 не закрывается. Зацепки для
   разметки из PR #72: две версии одной справки в подкаталоге ТКП (движок дал
   предупреждение «неоднозначность»); пара «старое/новое» свидетельств налогового
   учёта разных регионов во втором пакете; КПП с ведущим нулём в документах опыта.
2. **#21** протоколы исходов по обоим пакетам — без них факт выигрыша не подтверждён.
3. **#23** каталог сроков «свежести» — без него класс `freshness` печатает
   «не проверяется», и это надо сохранять в отчёте замера, а не скрывать.
4. **#19** закупочная документация второго заказчика — без неё по нему работает
   только опись и внутренняя консистентность.
