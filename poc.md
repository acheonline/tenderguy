# poc.md — Эпики Proof of Concept (только базовые функции)

**Источник:** `issues.md` (эпики E0–E8), `mvp.md` (минимальный срез MVP), `analyze.md` (риски AR-xx)
**Роль:** senior system & business analyst
**Дата:** 10.11.2026
**Статус:** v0.1 — границы PoC к утверждению заказчиком

> PoC — **не продукт и не часть MVP**. Это проверка осуществимости на реальных документах: ответ на вопрос «способна ли гибридная схема (правила + структурное сопоставление + LLM) находить типовые дефекты заявок с приемлемым качеством». Всё, что не проверяет эту гипотезу, — вне PoC. Результат PoC — письменное заключение go/no-go для MVP (`mvp.md`) с замерами качества, а не работающая система для пользователей.

## Гипотезы, которые проверяет PoC

| # | Гипотеза | Проверяемый риск (analyze.md) | Как проверяем |
|---|---|---|---|
| H1 | Закупочную документацию и пакет заявки (PDF/DOCX/XLSX/сканы трёх заказчиков) можно разобрать с качеством, достаточным для проверок | AR-2 | Эпик P1: прогон 3–5 реальных комплектов, замер качества извлечения |
| H2 | Заявленные боли («неверный юр. адрес, КПП», «истёк срок свежести», «нет документа в составе») детектируются **детерминированными правилами** без LLM | AR-1 | Эпик P2: правила + сверка с эталонными реквизитами на реальных пакетах |
| H3 | LLM находит расхождения «форма ↔ инструкция» и семантические дефекты, с цитатой-источником и приемлемой точностью | AR-1, AR-21 | Эпик P3: 2–3 класса семантических проверок на размеченных кейсах |
| H4 | Результаты, найденные системой, совпадают с дефектами, которые нашли люди (протоколы отклонений, версионная история «косячных» заявок) | AR-9, AR-15 | Эпики P0 + P4: сравнение с ручной разметкой |

## Состав PoC: эпики

| Эпик | Название | Прототип какого эпика issues.md | Базовый функционал |
|---|---|---|---|
| **P0** | Данные PoC | E0 (инвентаризация), E5 (golden set) | Сбор 3–5 реальных кейсов на заказчика: закупочная документация + поданная заявка + исход (выиграна/отклонена с причиной). Разметка дефектов «вручную, как нашли мы» по agreed-каталогу классов. Мини-эталон: 5–10 размеченных пакетов — не процесс golden set, а разовая разметка |
| **P1** | Парсинг документов | E2 | Загрузка файлов с диска (без веб-интерфейса); извлечение текста, таблиц, пагинации; карточка документа с атрибутами (тип, ИНН, КПП, ОГРН, даты, суммы); привязка фрагмента к «документ + страница/пункт». Замер доли успешно разобранных документов |
| **P2** | Детерминированные проверки | E3 (уровень 1), E4 (правила, мастер-данные) | Эталонные реквизиты юр. лица — в конфигурационном файле (не система мастер-данных); правила как данные (состав пакета, сверка реквизитов, сроки «свежести»); прогон по пакету; вывод замечаний с источником |
| **P3** | Семантические проверки (LLM) | E3 (уровень 2–3), E4 (База знаний) | 2–3 класса: форма ↔ инструкция по заполнению; наличие требуемого документа ↔ описание требования в документации; одно содержание-по-сути. Каждая модель-кандидат (≥2, по Spike C) прогоняется через один и тот же набор; вывод — цитата, confidence, «требует подтверждения» |
| **P4** | Протокол результатов и go/no-go | E6 (отчёт), E5 (метрики) | Отчёт — markdown/консоль (без веб-UI): замечания по классам с severity и источником; таблица «найдено системой ↔ найдено человеком ↔ пропущено ↔ ложное»; замер precision/recall на мини-эталоне P0; письменное заключение: какая доля дефектов формализуема правилами, где LLM необходим, где вреден; рекомендация go/no-go по MVP с параметрами среза |

Порядок: **P0 → P1 → P2 → P3 → P4** (P2 и P3 могут идти параллельно после P1).

## Явно вне PoC (базовые функции только)

- Веб-интерфейс, рабочее место специалиста, роли, аутентификация, журнал доступа.
- Продуктовая инфраструктура: контур, CI/CD, хранилище, мониторинг (E1 целиком).
- Система мастер-данных и реестр правил с версионированием/владельцем (в PoC — конфигурационные файлы).
- Полный golden set, регрессия в CI, canary (формализация E5 — в MVP).
- База знаний нормативки (44-ФЗ/223-ФЗ, Положения о закупке) — в PoC правила и требования берутся из документов конкретного кейса, не из БЗ.
- Sign-off, статусы устранения, экспорт отчёта, уведомления, дашборды.
- Любые интеграции, ЭП, генерация документов, мониторинг закупок (E7/E8).
- Решение ИБ по контуру (P0-6): PoC работает на обезличенной/синтетизированной выборке либо на данных, обработанных в согласованном с ИБ временном контуре — фиксируется до начала P0.

## Критерии успеха PoC (пороговые, к утверждению)

| Критерий | Порог | Гипотеза |
|---|---|---|
| Доля документов комплектов, пригодных для проверок после парсинга | ≥ 80 % | H1 |
| Recall детерминированных классов (реквизиты, свежесть, состав) на мини-эталоне | ≥ 0,90 | H2 |
| Трассируемость замечаний (фрагмент-источник) | 100 % | H2, H3 |
| Precision семантических классов LLM | ≥ 0,60 (порог ниже MVP — PoC измеряет потолок, не принимает качество) | H3 |
| Совпадение с дефектами, найденными человеком, на «косячных» заявках | измеряется, порога нет — вход для калибровки E3/E5 в MVP | H4 |
| Заключение go/no-go с рекомендованным срезом MVP | выпущено | все |

PoC считается завершённым при выпуске заключения P4 **независимо от результата**: отрицательный результат по H1–H3 — тоже результат, экономящий бюджет MVP (митигция AR-1, AR-2, AR-9 до крупных вложений).

## Входные данные, требуемые от заказчика для старта P0

Минимальный набор (из чек-листа Discovery, `analyze.md` раздел 7):
1. 3–5 полных кейсов на каждого из трёх заказчиков: документация + заявка + протокол с исходом (включая отклонения с причиной).
2. Карточка(и) юр. лица: реквизиты, лицензии, сертификаты со сроками — для эталона P2.
3. Каталоги требуемых справок со сроками «свежести», если ведутся.
4. Согласование обработки документов в контуре PoC (см. «вне PoC», последний пункт).
