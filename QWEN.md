# tenderguy — контекст для агентной разработки

Go 1.24.4. Система подготовки и проверки пакетов тендерных заявок (44-ФЗ/223-ФЗ).
Фаза PoC: реализован обход каталога и парсинг .docx/.xlsx/.pdf, извлечение реквизитов,
привязка фрагментов к адресу документа. Источник постановок — GitHub Issues
`acheonline/tenderguy` (`[P*]` — задачи PoC, `[DATA]` — сбор данных, `[E*]` — эпики MVP).

## Гейты: как проверять себя

```bash
gofmt -l .                                       # пусто
go build ./...
go vet ./...
"$(go env GOPATH)/bin/golangci-lint" run ./...    # бинарник НЕ в PATH
go test -race -coverprofile=coverage.out ./...
go tool cover -func=coverage.out | tail -1         # ≥ 70 % на критичные модули
```

Все прогоны обязательны до отчёта «готово». Вывод передаётся дословно: падающий тест —
в ответе, а не «почти проходит». Утверждения без доказательства выводом не делаются.

## Правила кода

- Каждая ошибка обработана явно; `_ = err` запрещён (lint падает).
- Тесты table-driven, stdlib `testing`, без новых зависимостей.
- Коммит: `[P1.2] Добавлен парсинг .docx`. PR задачи `[P*]` обязан содержать правку
  `README.md` — раздел с командой запуска, флагами, примером, ожидаемым результатом и
  кодами выхода. Без этого PR не готов.
- Библиотеки зафиксированы: docx — `github.com/nguyenthenguyen/docx`, xlsx —
  `github.com/xuri/excelize/v2`, PDF+OCR — `github.com/otiai10/gosseract` (Tesseract).
- `docs/` в `.gitignore`: это клиентские документы заказчиков (НЭО, ТЭК СПб,
  Техснабэкспорт, ТГК-1). Они не коммитятся, не пушатся, не попадают в PR и не используются
  как тестовые фикстуры. Фикстуры — base64-константы в `_test.go`.
- Значения ключей (DashScope, PAT) не выводятся и не записываются в файлы репозитория.
- Пути к документам только из флагов CLI.

## Разделение с CI-ботом

Headless-агенты в GitHub Actions (`qwen.yml` по комментарию в issue, `autofix.yml` при
падении «Go CI») ведут узкие правки, полностью описанные в теле issue, и не трогают
архитектуру. Всё, где нужен выбор структуры модулей, работа с реальными пакетами
документов или решение по трактовке 44-ФЗ/223-ФЗ, — локальный конвейер с человеком.
Headless-агент не открывает PR, если в issue нет чек-листа критериев готовности.
Доставка — `git push` + `gh` (не MCP `push_files`: он искажал длинные base64-блоки).

## Оркестрация агентной разработки

Главный агент — текущая интерактивная сессия. Она декомпозирует задачу, делегирует
исполнителям, проверяет их выводы и отвечает за честность отчёта. Порядок на одну задачу
из issue:

1. `gh issue view <N>` — цель, скоуп, критерии готовности. Нет чек-листа — сначала дописать,
   не начинать реализацию.
2. План (файлы-мишени, зависимости, риск) — **показывается человеку до первой правки**.
3. Работа в отдельной ветке; параллельные задачи — только через `git worktree`, один писатель
   на дерево.
4. Код → тесты → гейты выше → ревью (read-only, отдельный агент) → фикс блокирующих →
   README → commit → push → PR → `gh run watch` «Go CI».
5. **Мерж и закрытие issue — только человек.** Сессия показывает вместе со ссылкой на PR
   head ветки (`git rev-parse HEAD`) и `git status --porcelain`: мерж при незакоммиченных
   правках или до конца раунда фикса теряет последний коммит — он повисает на закрытом PR
   (прецедент #51 → догоняющий #53). После мержа — проверка
   `git merge-base --is-ancestor <sha> origin/main` и чекпоинт в память проекта.
6. Прогон без открытого терминала — через `tender-session` (`start <slug> "/tender:task N"`,
   `attach`, `logs`): оркестратор живёт в tmux, разрыв SSH его не касается, консоль дублируется
   в `/tmp/tender-<slug>.log`. Одна сессия = одна ветка: параллельные задачи лончер расводит по
   `git worktree`. Мерж дополнительно закрыт в `permissions.deny` (`gh pr merge*`) — оно действует
   при любом режиме, в отличие от подсказок классификатору.

Роли: кодер реализует и сам прогоняет гейты; тестировщик закрывает критерии теста
(написанный им тест не считается доказанным, пока он не увидел его вывод); ревьюер
даёт только вердикт и не правит код.
